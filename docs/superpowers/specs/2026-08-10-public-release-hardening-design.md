# QiDao 公开发布加固设计

## 目标

在不改变实时对弈分析产品流程的前提下，将当前工作树整理为可公开审查、可复现构建且不包含本机敏感材料的源码仓库，并修复审计中已经复现的发布阻断缺陷。

## 发布边界

- 提交 Swift、Rust、Python 源码、测试、配置、文档和两个自训练的轻量 ONNX 视觉模型。
- 不提交 KataGo 大模型、签名证书、私钥、keychain、构建产物、虚拟环境、DMG、归档或生成的静态库。
- 保留 `katago/analysis.cfg`、网络许可证和推荐模型的 SHA-256；README 指导用户自行安装 KataGo、下载模型并在应用中选择路径。
- KataGo 模型缺失不能导致本地应用构建失败；运行时通过现有 AI 设置界面完成配置。
- 未建立 fork 专用 Sparkle 密钥、更新源和受保护发布环境前，不发布可执行的自动更新配置或生产签名工作流。

## 必须修复的问题

### 视觉状态恢复

- 整盘恢复必须分别验证新增、删除和变色差异；任何已确认棋子被删除或变色但复核帧为 `unknown` 时，不允许覆盖 QiDao 棋盘。
- 提子归一化必须使用“最后落子方”，不能把“下一手方”传入状态机。
- 停止或重启追踪后，旧扫描结果不得继续提交到新会话。

### Swift/Rust 边界

- UI 和 core 只接受产品实际支持的 9、13、19 路棋盘。
- 跳转手数、候选数和 KataGo 返回坐标必须在转换或数组访问前校验范围。
- 明确区分 KataGo 的合法 `pass` 与超时、EOF、协议错误；引擎错误不能写入一手虚假停着。
- 引擎停止需要有超时及强制终止兜底，避免后续启动永久等待。
- 编辑祖先局面后必须使后代棋盘缓存失效。

### 发布安全

- 扩充 `.gitignore`，覆盖签名、证书、keychain、notary、Sparkle 下载缓存、静态库和 KataGo 权重。
- 移除个人绝对路径；README 明确依赖、模型获取、首次配置和无模型时行为。
- 当前上游 `appcast.xml` 不进入发布提交；生产 release workflow 在 fork 密钥与权限边界完成前禁用。
- 发布用 Info.plist 必须包含录屏用途说明。

## 数据流与失败行为

视觉帧先经过定位、交叉点分类和多帧复核，再由围棋状态机生成候选局面。只有新增、删除、变色三类差异均得到足够证据且规则合法时，候选局面才能作为单一事务写入 QiDao。任何不确定差异都保留当前棋盘并继续采样，不做部分覆盖。

KataGo 配置缺失时，应用仍可启动、编辑棋谱和使用实时识别，但 AI 区域显示可操作的配置提示。引擎返回明确 `pass` 时才记录停着；其他错误进入错误状态并保留棋局。

## 验证标准

- 为视觉误删、最后落子方归一化和停止会话竞态增加回归测试。
- 为受支持棋盘尺寸、非法跳转、非法候选数、越界 AI 坐标、pass/错误区分、缓存失效和引擎停止增加最小回归测试。
- 运行全部 Python 视觉测试和 Rust 测试；若本机工具链缺失，明确记录未执行项，不能声称通过。
- 使用项目本地构建脚本验证无 KataGo 大模型仍能构建应用。
- 执行敏感信息、绝对路径、忽略规则、大文件和最终暂存清单复查。
- 最终 Git 历史不得包含 `.signing`、私钥、证书、生成静态库或 KataGo 大模型。

## 非目标

- 本次不重新训练视觉模型。
- 本次不建立 Apple 公证、Sparkle 私钥或生产发布环境。
- 不处理审计中与公开发布无直接关系的低优先级 UI、SGF 兼容性和性能重构；这些问题记录在审计文档中供后续处理。
